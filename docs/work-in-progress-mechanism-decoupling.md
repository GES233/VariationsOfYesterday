# 临时施工备忘：机制解耦与玩法讨论接续

> 更新：2026-11-12。状态：**第一批（阶段 B 结构解耦）、第二批（阶段 C-1 消费者事实分账 + 旧文档同步）与第三批（阶段 C 首个玩法变化：短时锁闭期菌塘只停长）均已实施 2026-11-12；其余玩法仍待讨论**。
> 用途：保存本轮会话的设计共识、源码审查发现、候选施工顺序与开放问题，供上下文压缩或后续会话接续。
> 本文不是新一轮机制定稿，也不是立即改动代码的指令。当前任务仅为落盘备忘，下一步继续讨论玩法。实施记录见 §9、§10、§11，配套职责表见 [mechanism-state-responsibilities.md](mechanism-state-responsibilities.md)。

## 1. 接续会话时先读这里

- 敲钟最初由 **Gemini 在一次会话中作为最小实现提出**，并非用户原先确立的核心玩法；后续迭代逐渐把它及其依赖固化。不要再以“敲钟原本是核心，现在退居辅助”为前提。
- 用户认可一个新颖点子或批准一次实现，不等于批准它成为全局玩法支柱，也不等于它附带的所有依赖永远固定。不要把本备忘里的候选方案再次自动定稿。
- **敲钟、庇护失效／到期、耐受、过载都可以存在，但不必咬合成固定的日常续期闭环。** 解耦不等于删除这些机制，也不等于禁止它们在特定情境中相互作用。
- 相位可以继续是世界内部的动力学性质；玩家是否直接读它、是否精确操作，应由具体玩法决定，不必沿用现有刻度敲钟模式。
- 用户提出：需要精确操作时，可以结合星象等世界条件；这仍是方向例子，**尚未批准具体天象系统或天象与地脉的因果关系**。
- **目前没有需要兼容运行的旧存档。** 本轮改造不以旧档迁移、兼容读取或保留旧字段为前置工作；新机制自身的保存与读取正确性仍需保证。
- 精确时机未来也可以和复杂 routine 绑定，甚至成为字面意义上的“变奏曲”音游。**本轮只记录一句远期可能，热度高后再考虑；不排期、不搭框架、不预留复杂接口。**
- 用户接下来要讨论玩法。继续时应先承接玩法问题，不要因为已有施工清单就直接修改机制。
- **后续用户确认：事件 → 机制（1..n）→ 效果。** 钟到效果之间的多种因素应解耦；用户原本就计划用专门的“转义层”处理这项工作。详见 §2.1，具体实现尚未定案。

## 2. 已达成的方向与尚未作出的决定

已达成的方向是：让各机制分别成立，根据场景选择组合；先判断玩家需要理解与完成什么，再决定技术机制如何服务它。精度可以来自对世界条件、因果与行动顺序的辨认，也可以在特定内容中来自操作时序，不要求所有日常活动都承担精确相位操作。

尚未决定：庇护的来源、寿命与范围；耐受适用于什么对象和刺激；过载造成什么损伤；钟有哪些具体用途；哪些经济活动受哪些环境条件影响；是否及如何采用天象、复杂仪式或其他设施。本文后面的拆分建议不是这些问题的答案。

### 2.1 后续补充：跨代载体、脉冲来源与转义层

**用户确认的来历与方向：**

- 钟最初承载的是一个“从旧时代延续到新时代、可以维系山”的跨代存在；它是在尚未与菌落脉冲、酸性山脉排水接线时形成的过渡产品。不能倒过来将其起源解释为专用生物电脉冲装置。
- 采用“钟 → multiple factors → 效果”的理解：中间因素应能分别表达和组合，不把所有作用固定在钟的身份上。总体方向是 **事件 → 机制（1..n）→ 效果**。
- 用户原本就计划专门做一个“转义层”处理上述映射；这不是本轮助手新提出的架构。当前确认其职责方向，尚未确定接口、数据结构或执行方式。
- 正脉冲保留两类来源情境：其一可以自发产生脉冲；其二不能自发产生，但人尚未失能，能够规律性提供外部脉冲。不能把这一认可扩大成“所有地区都必须由玩家手动定时敲钟”。
- 输入介质和刺激效果可以更丰富。存在正脉冲，不自动意味着必须同时续庇护、增加耐受或触发统一经济档。

**待讨论的职责划分建议（不是已确认实现）：**

- 转义层结合事件、作用介质与当地状态，选择适用机制并形成具体输入或状态变化；不只是给旧的硬编码分派换名称。
- 同一事件可以作用于多个机制；不同事件也可以经不同介质作用于同一机制。机制之间不默认全部互相触发。
- 外部刺激与内生脉冲在来源和作用路径上区分：内生尖峰已在模拟中发生，不应为了复用“脉冲”事件再向原细胞注入一次外部刺激。需要共同消费它们的机制可使用发生事实，并保留来源差异。
- 由动力学演化产生的效果，应通过输入与实际演化获得；由明确玩法规则产生的效果应标明其规则依据，不预先把“这次刺激必定有益／必定推迟尖峰”写进转义结果。
- 来源是否共享同一套耐受、过载和庇护规则，仍需逐项讨论，不能仅凭“都是正脉冲”认定完全等价。

### 2.2 后续补充：主动显式化状态与转移

**用户提出的方向：** 受到“找到项目中所有隐式状态机”的清理思路启发，希望在本轮设计时主动形成显式状态与转移，避免规则继续隐含在多个回调、标签和计时字段里。用户认可前述过载／生态死亡拆分示例的大方向；具体暂停生长、损伤量等玩法参数仍未定案。

**实现建议，尚未实施：**

- Mandate 可作为完整领域状态的主体，连续动力学继续由积分器推进；离散机制分别明确状态、事件、条件、转移与效果，不强制把整个世界变成一个有限枚举。
- 区分三种信息：必须保存的机制记忆（如期限、已发生损伤）、由当前事实推导的分类（如是否过载／相位可读）、转移产生的一次性效果。可推导标签不默认复制成另一份可变真值。
- 当前已有局部显式转移：`PulseToleranceState.onPulse` 返回新状态与裁决。问题不全是缺少状态机，而是状态职责捆绑、下游解释和跨层转移仍不够明确。
- 转义层负责解释具体事件，机制负责自己的状态转移，actor 负责有序提交，游戏接线执行效果。具体函数签名和模块布局待设计；不因此引入状态机框架或全量事件溯源。
- 为每个有历史依赖的机制列一张转移表：当前条件、事件／时间推进、守卫、状态更新、效果、恢复条件、状态拥有者。明确同时命中规则时的顺序或冲突处理。
- 显式记录跨机制关系，例如“短时过载是否暂停生长”与“损伤达到条件才允许永久枯萎”，避免通过复用标签隐式建立后果。独立状态可以并存，不列举全部状态的笛卡尔积。
- 对时间到期的语义作明确选择：只需查询当前是否有效时可以由期限推导；如果到期必须触发一次性效果，则显式记录处理进度或安排到期转移，避免每次读取反复触发。
- 接口目标可概括为“状态＋事件／时间／必要环境输入 → 新状态＋发生事实／待执行效果”；所有影响结果的时间、随机输入和环境信息需明确提供，不依赖隐藏读取。发生事实再参与其他机制时应有明确处理顺序，避免重复施加物理刺激。

该方向不构成即刻开展全仓重构的指令。先以一条具体机制链说明和验证，再决定实施范围。

## 3. 当前代码事实：为什么不只改敲钟窗口

以下是本轮静态源码审查发现，尚未通过新的运行实验验证。路径以仓库根目录为基准。

### 3.1 钟一次触发了多项职责

`mandate/BellRitual.scala` 的 `BellStrikeOutcome` 同时携带重锚、`c0` 值、脉冲面积、心跳记账与过载惩罚；`mandate/MandateOverworld.scala` 执行这些效果。成功敲钟可设置整格 `baselineCalming = 0.03`，拆钟直接清零并注入应力。目前没有多来源维护的汇总语义。

这不是必须保留的物理定律。可以保留“设施／维护条件影响基线安抚”，而不继续默认“一口普通钟代表该格所有维持来源”。只有具体玩法确实需要多个来源时，再实现相应记录。

### 3.2 脉冲、庇护、耐受与过载共享记账路径

`inner/event/EventMsg.scala` 的 `FirePulse(..., heartbeat = true)` 既描述物理刺激，又选择是否进入玩法记账。`inner/veins/MandateAgent.scala` 的 `recordPulse` 调用 `PulseToleranceState.onPulse`；后者同时更新庇护期限、耐受和过载锁闭。现有 `heartbeat = false` 已证明物理输入可以与这份记账分离，但不能分别控制账本中的各项职责。

默认约 40 秒的庇护、8 秒最小间隔及其耐受数值属于当前实现，不是本轮重新确认的设计常量。

### 3.3 相位读数承担了部分玩法状态

`inner/veins/MandateReadout.scala` 中，`PhaseTracker` 会因 `effectiveA` 的脉冲修正或过载锁闭返回 `BurnoutNoCycle`。但 `MandateState.equ` 的恢复偏移仍由 `s`、`M` 等计算，脉冲通过快变量输入进入方程。

因此，当前的过载判定不全是对数值轨道的被动观测；它也包含显式玩法规则。不能把所有 `BurnoutNoCycle` 都表述为方程已进入同一种慢性生态死亡状态。应考虑分别表达可观测相位、介质损伤和短时功能受限，再让消费者按需判断。

### 3.4 一个共享标签已经产生持续生态后果

`MandatePhenomena.evaluateGastrodiaBed` 把 `BurnoutNoCycle` 或菌网低于存活下限判为 `Withered`。`blocks/GastrodiaBedBlock.scala` 在生长检查发现该裁决时写入枯萎状态，之后即使环境恢复也需人工翻修。

所以短时过载期间如果执行了相应检查，可能留下持续的菌塘损失。这是需要明确讨论的机制依赖，尚不直接定性为 bug；不能仅因急性过载和菌竭共用“烧毁”标签，就默认它们拥有相同的生态后果。

### 3.5 经济与生态并非完全独立

`Readout.isMaintained` 综合脉冲庇护、菌网存活、无烧毁标签及无正向尖峰。`MandatePhenomena.classifyEconomy` 据此统一决定多个经济倍率。菌塘在生态条件允许生长后，还会调用 `MandateEconomy.suppressCropGrowth`，所以它也会受庇护经济档影响。

这些消费者应分别明确依赖的是长期土地健康、临时危险、设施服务还是特定庇护；不能只更改 `isMaintained` 的含义就认为所有下游行为自然正确。

### 3.6 叙事管线仍围绕旧干预形态组织

Elixir 的 `Witness` 把实测 `safe_tick` 绑定到物证，`Chronicle` 和卷宗结算围绕重锚载体、上游降扰等干预组织；`Pathway`、`Canon` 与正文模板有相应结构和内容约束。它们是独立工具原型，并不表示完整卷宗闭环已在游戏中接通。

如果玩法不再以“读刻度、重锚”为通用解法，必须同步审查这些内容依赖。保留证据可靠性，不必保留所有谜题的同一答案形式。

### 3.7 落地示例：过载与生态死亡（待讨论方案，未实施）

用户进一步询问这组共享标签如何落地。以下用于说明转义层职责，不视为已确认的玩法后果：

- 分别表达三类信息：菌网存活与损伤（依据 `M` 等实际状态）、刺激负荷／暂时过载（依据具体机制规则）、周期相位是否可观测（依据轨迹与测量条件）。它们可同时存在，不用一个互斥的“正常／过载／死亡”总枚举覆盖。
- `a_slow` 跨过当前模型的失能边界不直接等于菌网已经死亡；介质存活、动力学工作区间和相位可读性仍应区分。已有 `isEcologicalBurnout` 也混合了这些含义，不能仅换一个调用名就认为完成拆分。
- 事件进入转义层后，可分别触发实际脉冲输入与适用的负荷记账。内生脉冲不会因复用入口而再次注入原细胞；是否计入负荷由来源和机制规则决定。
- 临时过载对菌塘的一个候选结果是暂缓生长，解除后按当前生态条件重新判断；持续枯萎需要独立的损伤／死亡依据。也可选择短时过载不影响菌塘，这一点尚待定案。
- 若希望强烈或持续过载最终造成生态死亡，应显式实现并验证“负荷 → 损伤 → 存活下降”的因果路径；先核对现有 `p → v → q → s → M` 路径是否已覆盖，避免同一伤害重复累计。不能直接以 `phase == BurnoutNoCycle` 代替这条过程。
- 消费者分别取用相关事实：菌塘读取生态与生长条件，庇护读取其来源／期限／失效条件，玩家效果读取实际暴露与危险；不把过载默认转成全部系统的共同失败。
- 最小实现可先采用纯函数分类与显式结果字段，复用现有 `M`、脉冲账本和相位跟踪，不立即添加新的损伤条或通用规则引擎。确需状态记忆时再新增独立状态。
- 检查组合场景：活菌＋短时过载、低菌量＋无过载、慢系统失能但菌网未死、菌网死亡＋过载并存、仅缺周期参照。过载解除不能复活已死菌网，相位不可读不能自动造成菌塘永久枯萎。

## 4. 候选解耦边界

| 对象 | 值得拆开的绑定 | 值得保留的联系 |
| :--- | :--- | :--- |
| 钟与其他交互 | 一次动作默认同时重锚、发脉冲、续庇护、加耐受 | 特定交互在特定环境中产生明确效果 |
| 物理刺激与庇护 | 正脉冲天然提供统一庇护；庇护只能靠补脉冲续期 | 合适的输入可以参与建立某种庇护，具体规则另定 |
| 耐受与过载 | 正常维护必加耐受；耐受增加必然走向过载 | 介质状态影响响应；超出承受范围可产生后果 |
| 庇护与经济 | 所有经济活动统一挂在心跳是否过期上 | 生产活动与环境、设施及危险条件存在因果关系 |
| 读数与玩法裁决 | 用同一个相位枚举代替生态死亡和短时锁闭原因 | 玩家看到的征兆与真实状态一致，允许不完全观测 |
| 推理与操作形式 | 每条证据链都导向精确刻度敲击 | 推断可检验，操作产生的结果与证据承诺相符 |

## 5. 建议保持的架构约束

以下是基于现有架构的施工建议，不把具体方程、数值或内容数量提升为不可更改的设计原则。

1. **世界状态与干预后果之间有可解释的因果链。** 快慢反馈、损伤与恢复可继续作为基础；若改方程，需重测，而不是为剧情结果暗设无依据的状态跳转。
2. **数值事实、观测和规则裁决明确区分。** 仪器可以粗糙、档案可以失真，但不能不说明地让同一字段在不同模块代表不同事实。
3. **物质输运与事件耦合保持各自语义。** 两者可以组合，但不能因接口方便就把传播信号等同于搬运应力或菌网。
4. **核心继续不依赖 Minecraft；可变状态保持明确所有权。** 现有 actor 可继续串行处理多种独立状态，不需要为了概念解耦增加线程或微服务。
5. **跨层承诺可验证。** 数值契约和内容检查继续约束适用范围；24 候选、六结局、五跳以及安全刻度都是具体模型，不是必须永久维持的数字或形式。
6. **历史、观察、行动、预测和结算分账。** 改变未来不应静默覆写既定历史；未来游戏接线仍需实际验证这一点。
7. **新机制自身能正确保存与恢复。** 无旧档兼容要求不等于无持久化要求。

## 6. 架构承受能力与暂拟施工顺序

判断：**可以分阶段改，不必推倒数值核心。** 当前 `MandateState/Grid`、actor、纯裁决函数、经济桥接和独立内容工具提供了可用边界；主要困难在共享字段的语义、消费者依赖与内容承诺，不在文件是否已经分开。

施工顺序仅供玩法讨论收敛后使用：

### 阶段 A：先把玩法职责说清楚

- 为刺激、庇护、耐受、过载、生态损伤分别写清触发、持续、失效、恢复和可观察证据。
- 标记哪些组合是特定情境规则，哪些是真正通用关系；允许暂时没有某种组合。
- 不以现有字段名或枚举决定设计，不立即补新天象、音游或通用仪式框架。

### 阶段 B：整理状态和事件边界

- 拆清 `PulseToleranceState` 的职责及 `FirePulse.heartbeat` 所代表的多重含义。**（2026-11-12：结构层面已实施（行为不变）——已拆为 `PulseLedger`（`ShelterWindow` / `ToleranceBook` / `OverloadLock`）与 `PulseBookkeeping`（`Counted` / `PhysicsOnly`），见 §9。）**

## 11. 第三批实施记录（2026-11-12，阶段 C 首个玩法变化：短时锁闭期菌塘只停长）

> 定位：**第一处刻意改变行为的批次**。用户拍板（2026-11-12）：短时过载锁闭不应把菌塘锁存为枯死；锁闭期只暂停生长，解除后按当前生态条件重判。

### 11.1 本批做了什么

- `MandatePhenomena.isGastrodiaBedDeepDead` 改为 `M < max(floor, 1e-9) || (!isOverloadLocked && isOffsetBelowKnee)`：
  - 菌网死亡（`M` 低于存活下限）仍判 `Withered`，优先级最高；
  - 活跃锁闭掩蔽读数越膝原因（`isOffsetBelowKnee`），短时过载不再锁存菌塘；
  - 无锁闭时，读数越膝仍按原判据判枯死（§8.4 另一待拍板项，本次未动）。
  - **掩蔽的直接后果**：锁闭给菌塘一段临时保护，持续续锁会延长它；锁闭结束（或间隙中的一次评估）若读数仍越膝，仍会锁存枯死且不自动恢复。保护的是「何时评估」，不是「越膝无害」。
- `evaluateGastrodiaBed` 在枯死判定与常规停滞之间加入锁闭分支：`isOverloadLocked → Stalled`。菌塘方块（[GastrodiaBedBlock.scala](../src/main/scala/moe/chestnut/awa/voy/blocks/GastrodiaBedBlock.scala)）只在 `Withered` 裁决时写 `condition = 2`；**未锁存**的塘在 `Stalled` 时写 `condition = 1`、恢复 `Growing` 时回到 0，锁闭解除后自动重判。**已锁存为 2 的塘不会被 Stalled/Growing 覆盖**，仍只能人工翻修（C14）。
- **重铺门槛保持改判前语义**：`canRefurbishGastrodiaBed` 改为直接使用 `!isBurnoutPhase && M >= max(floor,1e-9) && s < 毒性阈值`（即旧判决提供的谓词），不复用带锁闭掩蔽的新判决；否则一个已锁存的死塘会在锁闭期变成「可重铺」，白费材料且与检查文案矛盾。测试补了锁闭期不可重铺的断言。
