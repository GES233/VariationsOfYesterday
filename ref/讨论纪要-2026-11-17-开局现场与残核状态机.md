# 讨论纪要：开局现场、工作残影与残核状态机

日期：2026-11-17。

状态：本轮讨论落盘。区分用户确定的方向、待验证建议与代码实际完成范围；不是完整开发排期。接续《讨论纪要-2026-11-15-主心骨与开局线索》（本地参考，不随本次提交）。`ref/` 默认被 Git 忽略，本文按用户要求单独纳入版本控制。

## 一、当前目标与范围控制

用户认为架构复杂度已经足够，代码工作应更多面向简化；元叙事已有小而自洽的基座。当前希望看清实际玩法会长成什么样，避免再次把“骨架已好、只缺皮肉”当成未经验证的结论。

此前返工的一个来源是不断加入新想法，例如剧情检查与约束、Kanren 引擎结合大六壬进行剧情推演。它们能与设定相接，不等于当前就应该实现。本轮没有授权恢复这些系统。

助手建议：用一个小而完整的可玩现场验证玩家的好奇、尝试与理解；新增内容优先服务这次验证。该建议尚不等于具体关卡已定稿。

## 二、传播阶段与玩家预期（已明确）

- 早期小范围引流以“这里发生过什么”为吸引点。
- 有一定知名度后，以“这里是一个活着的世界，它如何运作”为持续探索的吸引点。
- 此处的前后期首先指作品传播阶段，不应误写成每位玩家固定经历的两个教学阶段。
- 期望玩家感到“有意思，这个世界比我想的要大”，而非仅仅看见实体或感到模组崩坏。
- 剧情模式中，玩家最初可能按普通恐怖模组理解异常，随后发现并非鬼怪、祭坛式的解释。
- 这不排斥实体存在：实体可以是需要解释的证据，不能把“没有鬼怪”误写成“没有实体”。

## 三、开局与山谷（已明确）

- 保留原计划路线：出生点 → 最近的山谷。
- 剧情模式的棚子会塌；后续一般模式的棚子不会塌。
- Minecraft 水机制与模组兼容性预期不支持将水的上下游作为重要的叙事、导航依赖。
- 一座山谷规模足以承载一段故事；不同山谷有不同故事，不必为第一段内容立即铺开多座山谷。

## 四、过去、遗留与证据（用户给出的底层方向）

1. 过去的人试图治愈或控制，但失败了。
2. 遗留下来的是 s 与 c₀ 的转化语义，以及菌网与人类的互作。具体叙事对应尚未在本轮细化，不能擅自变更现有数值语义。
3. 菌网吞噬人类残存的意识，试图构建某种能够解决问题的新存在；屡次失败，留下实体；之后某次召唤到了玩家。
4. 玩家通过未知实体的行为、残存资料，以及仪器／设备接触这些线索。
5. 实体行为确定采用“过去某个人的工作残留”。不采用菌网主动设计解决方案的智能行为，后者要求的智力过高。

上述底层因果不等于开场需要一次讲明。助手建议首次发现停在“它似乎还在尝试完成某件事”，具体揭示节奏待定。

## 五、第一现场与表现形式（建议，尚待实作验证）

助手建议做一个设备旁重复工作的残影现场，让行为、资料和设备反馈互相印证：玩家先看到重复动作，再从工作记录理解用途，最后亲自操作设备，发现旧动作已不能完成原来的目的。

这只是结构建议，不代表已确定具体职业、动作、设备种类、读数或设备与实体的联动机制。

表现方案建议为极简自定义实体承载位置、朝向和动作，粒子表现轮廓缺损、拖尾与消散。先以固定工位动作循环验证，不默认加入寻路、仇恨、攻击、掉落或完整 Mob AI。尚未实现实体。

“靠近就沙化”不应妨碍玩家看清工作循环；确切消散条件尚未决定。

## 六、Minecraft 侧演出边界

用户提出棚子也使用粒子，并采用局部状态机／不应期，状态不进入 Agent，在 Minecraft 侧运行。

助手建议：棚子以初始方块承载碰撞与遮挡，消散时移除指定部分并播放粒子，保留残核；这不是本轮已完成的棚子实现。演出再触发冷却与模拟核心的不应期应分开命名、维护。

服务端负责全局状态与触发裁决，客户端负责表现；不逐粒同步。只有实际影响地脉的行为才走既有事件接口。粒子进度和演出冷却可留内存，已塌棚事实与玩家触发记录必须存档。

## 七、残核状态机（首版已实现；多核修订见第九节）

本节保留首版实现记录。“每个世界一个残核”仅描述首版单份状态对象，不再作为世界中物理核数量的限制；`Nourished` 的物理含义及后来者引导须按第九节拆分。

核的全局状态与玩家记录分离：

| 场景 | 核状态 | 玩家记录 |
| --- | --- | --- |
| 无玩家加入 | Dormant | 空 |
| 玩家加入但未触发 | Dormant | 该玩家未记录 |
| 首次触发后 | Spent | 记录触发者 |
| 触发后又有新玩家加入 | Spent | 新玩家未记录 |
| 被滋养的核 | Nourished | 不再驱动状态变化 |

- 加入本身不修改状态；不需要维护在线人数作为状态阶段。
- Dormant 首次触发进入 Spent，返回 CollapseShelter。
- Spent 下尚未触发的玩家得到 PersonalReceipt，并记录 UUID。
- 已触发玩家再次操作返回 AlreadyTriggered。
- Dormant 或 Spent 均可滋养为 Nourished；后者为终态，交互返回 Stable。
- 状态和 UUID 先提交，调用方随后执行对应反馈。
- 这里的“提交”是内存更新并标记待保存，不代表效果与磁盘保存之间有崩溃事务保证。

实现：`src/main/scala/moe/chestnut/awa/voy/mandate/overworld/ArrivalCore.scala`。

每个世界一个残核，通过独立 `voy_arrival_core` PersistentState 保存，不进入 MandateAgent，不改变地脉 schema。调用限定 Minecraft 服务端线程。

验证：`ArrivalCoreSpec` 四项测试通过，覆盖只查询不触发、多人仅一次塌棚、存档重载后补触发、滋养终态。

尚未接入：实际方块／结构、玩家加入或交互回调、线索与物品发放、滋养条件、模式选择、粒子、音效、演出冷却。当前模块不会自行生成棚子或改变游戏现场。一般模式不塌棚的要求已记录，模式接线尚未实现。

## 九、多核、毁核与玩家独立存在（后续讨论已确定）

现行口径同步至 `docs/CREATIVE_BIBLE.md` §6；工程现状与待改边界同步至 `docs/CURRENT_ARCHITECTURE.md` §4.1。本次只更新文档，未改动首版状态机代码。

- 核是菌网局部密集、高度组织化的结构；“维度更高”暂作创作理解，不新增技术维度或模拟系统。
- 可存在多个此类结构。仅一处承载开局引入玩家的历史，其他残核可随环境激活；激活不自动召唤玩家或重播开局。
- 玩家一旦被引入并成为游戏的一部分，就独立于菌网和核持续存在。菌网死掉、核被敲走不阻止玩家游玩、加入或按游戏机制重生。
- 核可移除，原址相应功能随之消失；恢复菌网不会自动重建核。掉落、搬运、重建与激活条件未定。
- 晚加入者仍应得到必要引导；核不存在时不得虚构核的响应。具体替代载体未定。
- 世界开局／个人引导记录必须与每枚物理核的局部状态分离；毁核不抹除历史，也不因放置其他核重置开局。
- `Nourished` 只终止开局流程，不代表永久供能或不可破坏。首版代码尚未完成这项拆分，也尚未支持毁核与多核接线。
- 小棚、空地、旧路的布局与“人类旧工作棚被菌网利用”均仍为建议，未确定建筑来源与细节。
